## Metric rules (carry over from the sheet unchanged — do not "improve" silently)
Definitions of terms: `D0` = first day in `ad_daily` at backfill (2026-05-06, stored `app_meta.daily_start`, never moves). `cutoff` = 2026-09-17 (`app_meta.lifetime_cutoff`). `data_through` = max(`ad_daily.day`) (2026-11-02 after backfill). For tracker family F, *mapped daily series* = rows of `ad_daily` whose `meta_family_key` maps to F through `meta_family_map.tracker_family_key`.

1. **Metrics are Meta-reported** (not Upstack new-customer): spend, purchases (`omni_purchase`→`purchase`→pixel purchase), revenue = conversion value.
2. **Attributed once per ad family, on its first tracker row.** First row = the row with the smallest `sheet_row` (tie: smallest `id`) within `(product_id, family_key)`. All other rows of the family carry 0 metrics. Rows with a blank ad family (`family_key` starts `id:`) always carry 0 metrics (their spend cannot be matched) but still count as unique ads.
3. **Since launch** (computed on the first row; `launch_date` is that row's date; NULL ⇒ all launch metrics 0):
   - if `launch_date >= D0`: sum of mapped daily rows with `day >= launch_date`;
   - else: `ad_lifetime(F)` + sum of mapped daily rows with `day > cutoff`.
   Per family: `spend`/`revenue` rounded to 2 dp; `purchases` rounded to integer (the sheet rounds per family before summing).
4. **Date windows.** `window` is one of: `launch` (default; rule 3), a trailing increment `1d|7d|14d|30d|60d|90d|180d` (N days ending at `data_through`, inclusive: `data_through-N+1 .. data_through`), `mtd` (1st of the month of `data_through` .. `data_through`), or a custom range given as `from=YYYY-MM-DD&to=YYYY-MM-DD` (both required; custom wins over `window`; a single day is `from=to`). Non-launch windows sum the mapped daily series (`family_daily`) over the window and are independent of launch date; no rounding beyond 2 dp. Daily data only exists from `daily_start` (2026-05-06) to `data_through`; a requested range is clamped to that span and the response says so (`window_info.clamped`, `window_info.note`). Windowed spend/purchases/revenue are attributed to the family's first tracker row exactly like rule 2. The fixed `spend_7d`/`cpa_7d` columns are always `data_through-6 .. data_through` (rule 8).
5. **Live now** = the family has `spend > 0` on `data_through` or `data_through-1` in its mapped series. Counted on the first row.
6. **Unique ads** at any level = `COUNT(DISTINCT family_key)` over the tracker rows in that group (family key = lower(ad_family) else `id:`+lower(concept_id)). Includes every tracker status (Briefing … Launched), same as the sheet's 1,464 rows / 1,434 unique.
7. **ROAS** = revenue / spend (null if spend 0). **CPA** = spend / purchases (null if purchases 0). Totals recompute from sums (never average ratios).
8. Same metrics at every level: `unique_ads, live_now, spend, purchases, revenue, roas, cpa, spend_7d, cpa_7d` (the 9 that tie to the sheet) plus `active_ads` (distinct families with spend > 0 in the selected window; equals families with spend since launch for `launch`). The window selection changes only spend/purchases/revenue/roas/cpa/active_ads; `unique_ads` is every ad in the group regardless of window; `live_now`, `spend_7d`, `cpa_7d` never change with the window.
9. **Meta→tracker family mapping.** Backfill loads `meta_family_map` from the sheet's `Meta Ads - Windows` tab (A→B, rule `sheet-windows`; blank B ⇒ unmatched). Meta families present in Daily but absent from Windows are resolved with the ported `Resolver` (from `~/lonvera-upstack-sync/meta_history.py`: exact / relaunch-encoded / ad-name / concept-prefix / product+type+version). ETL flag `--mapping sheet|extended` (default `sheet`): `sheet` uses only Windows-derived mappings so numbers tie to the sheet; `extended` adds resolver mappings for the rest. The loader MUST report the dollar delta between the two modes (since-launch spend and 7d spend per product). Going forward the daily ETL resolves new Meta families with the Resolver and retries previously unmatched ones.
10. **Unmatched Meta spend**: Meta families with `ad_daily` rows and no tracker mapping are assigned to a product by `products.meta_regex` (ordered by `meta_priority`, case-insensitive search on the Meta family name; sheet order bone→liver→bull→belle) else `unassigned`, and listed in `unmatched_meta` (windows 7d/30d/all, live).
11. **Tags.** `products.tag_set` picks the hierarchy: `linemap` (Vita Bull now) uses `ad_tags(tag_set='linemap', is_current)`; others use the tracker's own columns via `ad_tags(tag_set='tracker')` (cluster = tracker Market Cluster, icp = tracker ICP (persona) column, pain = tracker Pain Point; blank ⇒ literal `(none)`). A tracker row with no current tag in the product's tag_set is grouped as `(untagged)`. The UI must label tracker-tag products "Tracker tags — not line-mapped yet".
12. **Keys.** `concept_id` is text always (`0510` ≠ `510`). `row_key` = `concept_id` + `#` + ordinal among rows sharing (concept_id, ad_family) in tracker order. Sheet row numbers are never an identity.
13. **Tie-out target (Vita Bull, data through 2026-11-02):** 1,464 rows; 1,434 unique ads; 141 live; since launch spend $4,761,591 / 54,960 purchases / revenue $4,262,522 (ROAS 0.90, CPA $87); last 7d spend $17,728 / 168 purchases (CPA $105.52); Meta-VitaBull 7d spend not on the tracker $3,997 (21 families, mainly Brief2-2-Bull-398). Every level must equal the same level in the snapshot tabs `rollups` / `overview_metrics` / `tag_breakout` / `tag_map`.

# v1.1 additions (SUPERSEDE earlier text where they conflict): ad-level grain, campaigns, Testing vs Scaling

## Grain
`ad_daily` is **Meta ad × day** (see migration 001). Two sources:
- **Stage 1 (tie-out baseline):** sheet backfill, family grain: `ad_id = 'fam:'||meta_family_key`, `campaign_id=''`, `source='sheet'`. These numbers tie to the sheet.
- **Stage 2 (ad level):** `etl.meta_pull --days 185` pulls Graph insights at `level=ad` with `ad_id, ad_name, campaign_id, campaign_name, adset_id, adset_name, spend, actions, action_values, inline_link_clicks` (reuse `meta_history.py` pull/chunk/async logic; `date_start` is the account-timezone day), for both accounts, and **replaces every `ad_daily` row of each covered day** with ad-grain rows (`source='meta_api'`), upserting `meta_ads` and `meta_campaigns`. After the replace, family×day totals must reconcile with the sheet's Daily tab (report max |diff| per day; ~0 expected except the last ~3 days Meta restates). If the pull cannot complete for some days (rate limit), those days keep their `sheet` rows; the app then shows ad-level detail only where it exists and says so (a remainder row, see /ads). Daily runs re-pull the trailing 7 days.
- Per-ad lifetime (`meta_ad_lifetime`) comes from the Lifetime tab (it has Ad ID).

## Stage
`meta_campaigns.stage = 'testing'` if `lower(campaign name) contains 'test'` else `'scaling'` (identical to `meta_campaign_history.classify_stage`); recomputed on every pull. `family_daily.stage` is the stage of the campaign the day's spend ran in; sheet-backfilled days with no campaign are `unclassified`. Stage totals must reconcile with the snapshot `meta_campaign_history.json` (Lonvera Projections sheet `1qA0iRJkWp1fbY5b6N860eM88Vs0JRe_8VfPQciMaLKI`, tab `Meta Campaign - History`, row 2 header `Date|Account|Campaign ID|Campaign Name|Product|Stage|Spend|Impressions|Link Clicks|Purchases|Purchase Value`, data from row 3, dates are Sheets serials): per day, all-product Testing and Scaling spend from `ad_daily` must match that tab within 1% (campaign-level vs ad-level pulls come from the same API; larger gaps are reported).

## Query params and metric additions (all metrics endpoints)
- `stage=all|testing|scaling` (default all). With `testing|scaling`, `spend/purchases/revenue/roas/cpa/active_ads` count only that stage's days. For `window=launch` with a stage filter only classified days count (`window_info.note` says so).
- `m` gains `testing_pct` (testing share of classified spend, null if none) and `stage:{testing:{spend,purchases,revenue,roas,cpa}, scaling:{…}, unclassified:{spend,purchases,revenue}}` (always the full split for the selected window, ignoring the `stage` filter).

# v1.2 additions: comparison mode (window A vs window B)

Josh wants to compare date windows side by side (last 7d vs last 30d, this week vs previous week, any custom range vs any other).

## Params (every metrics endpoint: products, rollup, families, ads, campaigns, unmatched, ad detail)
- `compare=prev|1d|7d|14d|30d|60d|90d|180d|mtd` or `cfrom=YYYY-MM-DD&cto=YYYY-MM-DD` (custom B window). Window A is the normal `window`/`from`/`to`.
- `prev` = the window of identical length immediately before A (A = Oct 27–Nov 2 ⇒ B = Oct 20–26). The trailing presets for B end at `data_through` like A's presets (so A=7d, B=30d overlap — allowed).
- Comparison needs a date window for A: if A is `launch`, return `400 {"error":"compare needs a date window"}`.
- B is clamped to `daily_start..data_through` like A. Response carries `compare_info` next to `window_info` (same shape; `days` is the clamped length).
- The `stage` filter applies to both windows.

## Response additions
Every metrics object `m` (and every row-level metric block) gains, always: `spend_per_day, purchases_per_day, revenue_per_day` (A value ÷ `window_info.days`). When `compare` is active it also gains
`cmp:{spend, purchases, revenue, roas, cpa, active_ads, spend_per_day, purchases_per_day, revenue_per_day}` (window B, same semantics as A) and
`delta:{spend, purchases, revenue, roas, cpa, spend_pct, purchases_pct, revenue_pct, roas_pct, cpa_pct, spend_per_day_pct, purchases_per_day_pct, revenue_per_day_pct}` where plain keys are A − B and `*_pct` is (A − B) / B (null when B is 0 or missing). `unique_ads`, `live_now`, `spend_7d`, `cpa_7d`, and the stage split of the launch window are not windowed and carry no `cmp`. Totals rows get `cmp`/`delta` recomputed from sums (never averaged). Ad detail: `metrics.family.compare` (same shape as `metrics.family.window`) and `metrics.family.delta`.
Per-day normalization matters because A and B may have different lengths (7d vs 30d): the UI defaults to showing per-day spend/purchases/revenue whenever the two windows differ in length, with a toggle to show raw totals. ROAS and CPA are already length-independent.

# v1.3 additions: stage chips, % of spend, dropdown tree, Back

## Stage filter = include list (supersedes `stage=all|testing|scaling`)
`stage=` is a comma-separated include list from `testing,scaling,unclassified`; omitted or `all` = all three. Unknown value → 400. It is a global filter like the date range: it applies to every metrics endpoint at every level, including `/api/products`, totals, `cmp` blocks and the daily charts. `unclassified` = days with no campaign data (sheet-backfilled days); the UI shows that chip only when the window contains unclassified spend. At least one stage must be included (empty → 400). The UI renders Testing and Scaling as toggle chips in the global header bar (on = included), persisted in the URL (`stage=scaling`), and carried across every screen and drill; it sits beside the date range and Compare control on every page including the products landing. `m.stage` split and `testing_pct` remain the unfiltered split for the window.

## % of spend
Every `m` gains `spend_share` = row spend ÷ the response's total spend (`total.m.spend`; sums to 1 across the sibling rows of a flat table; in `/tree` it is relative to the root total of that response, so a child's share adds up to its parent's). With compare: `cmp.spend_share` and `delta.spend_share_pp` (A − B, percentage points). UI column "% of spend" sits right after Spend, formatted `12.3%`, sortable, shown in every table (clusters, ICPs, pain points, families, Meta ads as "% of family", campaigns, unmatched).

## Dropdown tree (expand in place) — new endpoint
`GET /api/products/<slug>/tree?root=cluster|icp|pain|family&cluster=&icp=&pain=&depth=0|1|2|3&window=…&stage=…&compare=…` → `{window_info, compare_info?, rows:[…], total:{m}}`, rows depth-first (parent then its children, each sibling group in default order). `root` = the level the table starts at (`cluster` = every cluster; `icp` needs `cluster`; `pain` needs `cluster`+`icp`; `family` needs all three); `depth` = how many levels BELOW the root to include (0 = root level only). Row: `{key, parent_key, level (0 cluster,1 icp,2 pain,3 family), label, cluster, icp, pain, family_key, primary_id, color, line_code, trigger, confidence, ad_type, status, thumb_asset_id, has_children, child_count, counted_here, m}`. `key` is a stable string (`cluster|icp|pain|family_key`). Meta ads (level 4) are NOT in `/tree`: the UI fetches them lazily per family with `/ads?family_key=…&cluster=…&icp=…&pain=…` (needs the same filters so rows add up). Totals and `spend_share` as above. The existing `/rollup`, `/families`, `/ads` endpoints stay (used for page-level drill and flat views); `/tree` must return the same numbers as them for the same level/filter.

# v1.4 additions: traffic metrics (impressions, link clicks, CTR, CPC; optional CPM, conversion rate)

**Schema:** migrations/003_traffic.sql (orchestrator-owned, already written): `ad_daily.impressions` (NULL = unknown), and on `family_daily`: `impressions`, `clicks_tr`, `spend_tr` (sums over rows with traffic data). API indexes go in `004_*` (not 003).
**Definitions:** *Link clicks* = Meta `link_click` action count (fallback `inline_link_clicks`), the same field the sheet's Daily tab already stores. *Impressions* = Meta `impressions`. **CTR = link clicks ÷ impressions** (link CTR, not Meta's all-clicks CTR). **CPC = spend ÷ link clicks** (cost per link click). Optional: **CPM = spend ÷ impressions × 1000**, **Conv rate = purchases ÷ link clicks**.
**Where the data comes from:** the Meta API pull (ad × day, `meta_pull`) fills `impressions` and `link_clicks` for every pulled day (`traffic_known`). The sheet backfill has link clicks but NO impressions (rows with `link_clicks = 0` are treated as unknown: old rows were never re-pulled), so `impressions` stays NULL on sheet rows until the Stage-2 API pull replaces those days. `build_metrics` fills `family_daily.impressions/clicks_tr/spend_tr` from rows with traffic data: API rows always; sheet rows only when `link_clicks > 0` (then impressions contributes 0 and that row is excluded from CTR via `clicks_tr` counting only rows with impressions; see below). To keep CTR consistent: `clicks_tr` = link clicks on rows where impressions is not NULL; `spend_tr` = spend on rows where link clicks are known (API rows, or sheet rows with clicks > 0); CPC = spend_tr ÷ (link clicks on those rows) — implement with one extra sum `clicks_all` if needed (add in a 004 migration; tell the orchestrator).
**Metrics object `m` gains:** `impressions, link_clicks, ctr, cpc, cpm, conv_rate` (ctr/cpc/cpm/conv_rate null when the denominator is 0 or unknown), windowed and stage-filtered exactly like spend. With compare: `cmp` and `delta` carry the same keys (`ctr` delta also as `ctr_pp`, percentage points).
**Since-launch caveat:** traffic metrics come only from days held in `ad_daily` (from 2026-05-06). For `window=launch` they cover days from `max(launch_date, daily_start)` and CPC/CPM use `spend_tr` as their base so the ratios are not polluted by pre-May lifetime spend; `window_info.note` says "Impressions, clicks, CTR and CPC cover days from May 6 only" (plus "impressions from <date>" while some days lack them). Totals recompute from sums.
**UI:** new columns in every table, order: Spend, % of spend, **Impressions, Link clicks, CTR, CPC**, Purchases, Revenue, ROAS, CPA. A "Columns" chip group above each table toggles groups: **Traffic** (Impressions, Link clicks, CTR, CPC; default on) and **Advanced** (CPM, Conv rate; default off); choice persisted in localStorage. Compare shows sub-lines like other metrics: CTR up = green (shown in percentage points), CPC down = green, impressions/clicks neutral gray. Meta-ads, campaigns and ad-detail tables carry the same columns; the ad-detail daily chart gets impressions and clicks toggles. Formats: impressions and clicks with separators, CTR `1.32%`, CPC `$2.74` (two decimals), CPM `$38.40`.
