# Creative priorities (`/priorities`, `python -m etl.creative_priorities`)

A weekly one-sheeter: per product (Vita Bull, Beef Liver, Boneflex) which **Market Cluster -> ICP -> Pain Point -> Story** lines to produce ads for next. Every row reads as a brief: the four tags first (full text, each with a one-sentence plain description built from the Communication Overview text), then a **status chip**, a then-vs-now line, the number of new concepts, the numbers, what competitors run, the reason and hooks. A legend at the top says what each tag is.

**Actions and Statuses (2026-11-10 redesign, read this first).** Every concept has exactly ONE **Action** (what to do with it) and ONE **Status** (how the line is doing), and the page prints the rule for each (the "What these mean" block under the product tiles, built from the API's `definitions`, i.e. the real thresholds in the constants at the top of `etl/creative_priorities.py`). The sections below this one were written with the old names; the table maps them.

| Action (JSON field `section`) | Meaning | Old section |
|---|---|---|
| `revive` Revive | Beat the product average 3+ weeks in a row (>= $200 a week, 1.10x the product over the stretch), now below it or switched off | `faded` (was working, now isn't) |
| `make_more` Make more | Status Working or Rising. ALL of them, ranked by the score, no row cap (the top 8 per product share the week's 8 new concepts, the rest show 0) | `iterate` (top 8 cap removed) |
| `test` Test | On our sheet with 0 to 1 ads run (under $1,000 spent); cap of 6 per product kept (removing it would list all ~50 untested lines and stop being a priority list) | `new` |
| `add` Add to sheet | Not on our sheet yet. Row field `source` = `Competitor` (angles competitors run that we have no line for, 3 per product) or `Our draft` (a proposal, 5 per product); shown under the Action chip, in the panel, in markdown and in the CSV column `add_source` | `proposal` + `competitor` |
| `stop` Stop | Enough spend ($5,000) and consistently below the product average, never had a strong stretch (5 per product) | `stop` |
| `hold` Hold | Everything else: average, too early, or not picked for another action. No action this week | `rest` (Everything else) |

Order on the page, in CSV and markdown: Revive, Make more, Test, Add to sheet, Stop, Hold (markdown leaves Hold out). A line that qualifies for more than one lands where the code always put it (the sets are disjoint: Revive needs a status that is not Working / Rising / Untested plus a working stretch; Make more is Working / Rising; Stop is Not working without a stretch; Test is Untested), i.e. Revive > Make more > Stop > Test > Hold.

**Statuses** (same `classify()` logic and thresholds; only the labels changed): Working, Rising, Fading, Not working, Average, Too early, Untested (old: WORKING NOW, RISING, FADING / WAS WORKING, NOT WORKING, AVERAGE / RUNNING AS USUAL, TOO EARLY, UNTESTED / UNDER-TESTED). The row's status is now always the line's own status: a Revive row used to show FADED / COLLAPSED / STOPPED as its status; that is now `revive_kind` (still used in the Revive text) and the status is whatever the line is (usually Fading). Add rows are Untested; the per-product "ads not mapped to a line" row is "No line"; manual concepts keep MANUAL. `Lines by status` counts every line and adds up to the total.

**Every row has the same detail panel, Hold included**: hooks (the line's own best ads), winning ads (`former_winners`, `winners_summary`), then vs now with the peak bar (`stretch`), the number tiles and competitor badges where present. The ETL attaches this data to every line row (Make more, Stop, Hold too); only Revive rows also carry the 3-step timeline and the revive play. Hold panels are still built when the row is first opened, but the content is the full panel. The "ads not mapped to a line" row keeps its own small panel.

**Key number** (collapsed row, plain English, product named, both numbers labelled): Revive "1.31x at peak. 0.62x now." or "... Off now."; Make more "1.12x last 30 days. Vita Bull average 0.74x."; Stop and Hold "0.80x since launch. Beef Liver average 0.91x."; Test "$240 spent so far" or "No spend yet"; Add the competitor text or "Draft". UI text says "since launch", not "lifetime".

**Old snapshots keep working (no rewrite, no migration).** Past weeks' snapshots, saved views (payload, row keys, briefed marks, saved filters), assignments' `section_at_assign` and manual concepts keep their stored old values. Every read goes through `etl.creative_priorities.norm_snapshot / norm_row / norm_key / norm_section / norm_status` (old -> new, idempotent): faded -> revive, iterate -> make_more, new -> test, proposal -> add (source Our draft), competitor -> add (source Competitor), stop -> stop, rest and other -> hold. The row key `product|section|cluster|icp|pain_point` is normalised on both sides, so a bookmarked old key, an old saved selection or an old briefed mark still resolves (a briefed toggle removes the old and new forms together). Manual concepts store the new values from now on (the form accepts the old names too). Cost: the snapshot is about 20% bigger and the build about 7% slower on a synthetic 165-line input (13.1 ms to 14.0 ms of compute; the database reads dominate on prod).

## Was working, now isn't (leads the sheet; the Revive action)
Defined from weekly history, not only a 31-90 day vs lifetime comparison. For every line the weekly ROAS is compared with its product's ROAS in the same week (`family_daily` by week, Monday-based). A **working stretch** = at least 3 consecutive weeks, each with line spend >= $200 and weekly ROAS at or above the product's, over at least $2,000 spend and with the stretch's ROAS >= 1.10x the product's over the same weeks; the line's **peak** is the stretch that earned the most revenue above the product average. A line is **was working, now isn't** when it has a peak and in the last 30 days it is idle (**STOPPED**: under $250 spend), below the product average (**FADED**), or below 0.90 index and at most 0.70x its peak ROAS (**COLLAPSED**). Lines strong over their lifetime but with no weekly stretch (their results predate the weekly data from 2026-05-06) also qualify, flagged "no sustained weekly peak". This includes lines that sit in NOT WORKING or AVERAGE today; only never-worked NOT WORKING lines go to the Stop list.
Each row shows: when it worked (week dates, ROAS vs the product's, CPA, spend); when and how it stopped (last 30 days ROAS / index / CPA / spend, % from the peak, last 4-week window at or above average); the former winning ads (lifetime spend >= $1,000 and ROAS >= the product's, now stopped or decayed: peak week, stop date, hook) and how many winners still work; a diagnosis worded "consistent with" (spend moved away / ads switched off; same ads fatiguing with few new launches; whole line weakening even with fresh ads; spend share fell while the line still runs fine); and a revive play (which former winners' hooks to remake, or rework the angle when the line weakens with fresh ads, and the concept count: 6 per product shared across the top rows, others listed with 0). Flags: thin (peak under $5,000), peak ROAS under 1.0x (above the product average, not above 1.0x), weak tags, no sustained weekly peak. Audience overlap cannot be seen at line level and is not diagnosed. Constants: `STRETCH_*`, `COLLAPSE_*`, `WINNER_MIN_SPEND`, `DECAY_RATIO` at the top of `etl/creative_priorities.py`.

## Status of every line (rates, same Meta-reported basis)
Index = the line's shrunk ROAS / its product's ROAS in the same window. Windows: lifetime (`ad_metrics`), last 30 days, and "then" = days 31 to 90 before the last day of data (`family_daily`). Constants at the top of `etl/creative_priorities.py`.
* UNTESTED / UNDER-TESTED: under $1,000 spend and at most 1 ad that reached $100. TOO EARLY: some spend but under $5,000, 40 purchases or 4 tested ads (not judged).
* WORKING NOW: 30-day index >= 1.0 and lifetime index >= 1.05 (or then >= 1.05 and now >= 1.05). RISING: 30-day index >= 1.05 and >= 1.15x the then index, or well above its lifetime.
* FADING / WAS WORKING: strong earlier (lifetime index >= 1.05 or then >= 1.05) and now below 0.90 or at most 0.85x its then index, judged only with >= $250 spend in 30 days; or idle (no spend in 30 days) with a lifetime index >= 1.05 (a retired winner). Rows say how much ROAS moved and the last rolling 4-week window in which the line was at or above its product's average.
* NOT WORKING: enough spend, lifetime index under 0.95 and 30-day index under 0.90 (or idle). AVERAGE: everything in between.

## Competitor signal ("what others are running")
Read-only input: the view `competitor_concepts` (written by the separate competitor job, which pulls the Meta Ad Library weekly and maps concepts to our taxonomy; this module neither scrapes nor stores competitor data). Contract columns: week_start, brand, concept_key, first_ad_start_date, days_running, variant_count, format, hook, primary_text_excerpt, mapped_product, line_code, cluster, icp, pain_point, confidence, is_new_angle, new_angle_label, as_of, is_stale. The snapshot reads the latest `week_start`; the Sunday step runs after the competitor step.
* If the view is absent, lacks a contract column, is empty, or errors, the signal and the competitor section are hidden (nothing breaks); the sheet then says no competitor ads are loaded.
* Each row shows "N competitors, N concepts, N running 60+ days (brands)". Untested lines that competitors run rank up in **New**; concepts that map to no line of ours (is_new_angle / no line) form **Competitor angles we have not made**. The sheet shows the as-of date and any stale brands (`is_stale`: the last pull failed, last good data kept).
* Running a long time is a signal, **not** proven performance; the sheet says so.
* Dry run with a file instead: `--dry-run --competitors-file FILE [--as-of DATE]` (a competitor CSV, or a .json of normalised rows).

## Proposed new market clusters (drafts; Add to sheet, source Our draft)
The sheet is not limited to existing lines. `etl/creative_priorities_proposals.json` holds drafts in the Communication Overview shape (product, market cluster, ICP, pain point, a story of 15 words or fewer in the existing voice, one-line descriptions, flag **NEW CLUSTER** or **NEW LINE inside <cluster>**, adjacent lines of ours as evidence, and match terms for competitor evidence). Seeded from the competitor pull's NEW lines and the ten angles Lonvera is not running (men on GLP-1, women's cycle and hormones, chest fat as cortisol / estrogen, "not beer, a tired liver" for men 55+, wild vs farmed, bone marrow for menopause joints, premature grays / copper, postpartum and kids' nutrition, stack consolidation, Spanish-language joints). Edit the file to add or retire drafts; a draft whose ICP already exists on the sheet for that product drops out by itself, so approving one (adding it to the Communication Overview) removes it.
They appear as status PROPOSED (draft), top 5 per product, 1 concept each, ranked 50% by the adjacent lines' results (economics x size, working lines only) and 50% by competitor activity (long-running concepts and brands matching the draft). Evidence is competitor activity and our adjacent results only: **no performance numbers are claimed for a proposal.** Drafts are for Josh's approval; they are stored in the weekly snapshot and the CSV (section `proposal`) like every other row.

## Iterate (the Make more action): who qualifies and how it is ranked (all constants at the top of `etl/creative_priorities.py`)
Qualifies when its status is WORKING NOW or RISING (see above; this already requires spend >= $5,000, >= 40 purchases and >= 4 ads that reached $100, a shrunk ROAS index so luck on a small sample cannot qualify, and a 30-day index at or above the product's).

Score (0 to 100) = 35% economics + 20% hit rate + 20% room to iterate + 15% momentum + 10% size, times (1 - 0.35 x share of the line's spend on weak tags):
* economics: blended index (half since-launch, half last 30 days) mapped 0.95 -> 0, 1.40 -> 1;
* hit rate (scoring only, constant `HIT_SPEND` = $1,000): shrunk share of mature ads (>= 14 days old, judged) that reached $1,000, as an index to the product's, mapped 0.75 -> 0, 2.0 -> 1;
* room: 1 - (line's share of the product's new ads in 30 days / line's share of the product's spend), floored at 0: lots of spend, few recent launches = room;
* momentum: 0.5 + (last-30-day ROAS / prior-30-day ROAS - 1), clamped, 0.5 when either window is under $1,000;
* size: log scale from $5,000 (0) to $25,000 (1).
Top 8 per product. **Concepts** = 10 per product (4 more for Revive, 6 for New: 20 in all) split by score with largest remainder, 1 to 5 per row.

## New (the Test action): who qualifies and how it is ranked
A taxonomy line with status UNTESTED / UNDER-TESTED and at most 3 tagged ads in the tracker (more means it is already in the pipeline). Lines added to the sheet after the ads were tagged (`added_after_tagging`) are skipped: they read 0 ads by construction.
Score = 50% adjacent winner + 20% cross-product + 20% Josh's cluster order + 10% has a story; with competitor ads loaded: 40% adjacent + 15% cross-product + 25% competitors (long-running concepts and brands) + 12% cluster order + 8% story. Adjacent = a *proven* line (>= $5,000, index >= 1.05) on the same product with the same ICP (weight 1.0) or only the same cluster (0.7); cross-product = a proven line on another product with the same pain point (1.0) or cluster name (0.6); each valued by its economics x size x (1 - weak-tag penalty). Lines with no evidence at all are shown only to fill a product to 3 rows, flagged "no performance evidence". Top 6 per product, 6 concepts split 1 to 2 per row. No numbers are invented: an untested line shows no ROAS.
**Hooks** for a new line are copied only from the same product's adjacent winner (another product's hooks do not transfer); for an iterate line they are the line's own best ads (>= $1,000 spend, ROAS at or above the product's, by revenue above that bar, duplicates collapsed).

## Confidence and flags
`thin sample` (< $10,000 or < 100 purchases), `weak tags` (> 35% of the line's spend on low-confidence, copy-only or auto tags; auto tags are `tagger auto-...`), `few ads` (< 8 judged), `Upstack new-customer ROAS below product average` (index < 0.85 on >= $3,000), `dormant`, `fading vs prior 30 days` (< 75%). Confidence: low with 2+ risk flags, high with none and >= $25,000, else medium. Each iterate row also shows ROAS on strong tags only.

## Known limits
* Meta-reported ROAS runs above actual new-customer ROAS; the Upstack figure beside it is the cross-check.
* Offer / sale lines (Offer / Price-Led, "50% off" ads) carry generic copy, so their ICP tags are often low confidence: they top the list on economics but with weak tags (penalised and flagged).
* "New" is judged on the tag, not on a text search of ad copy.
* Recent ads (< 14 days) are left out of the hit rate; mass relaunch days count as launches.

## What the tiles and hit-rate numbers mean (2026-11-10)
* **Words.** ROAS = Meta-reported purchase value / spend. CPA (cost per purchase) = spend / purchases. **All time** = since each ad launched; **last 30 days** and **last 14 days** = the days ending on the data-through date. Upstack new-customer ROAS is a separate measure (row panels only).
* **Funnel (display).** *Launched* = every ad (first tracker row of an ad family in `ad_metrics`) that has a Launch Date or any spend. Of those: *under $100* spend (never really tested, includes launched ads with $0 spend), *tested* = $100+ (`JUDGED_SPEND`), *hit* = $10,000+ (`TOP_SPEND`). **Hit rate = hits out of all launched ads** (tiles read "115 of 1,463 launched (7.9%)"; every launched ad counts, recent ones included); "115 of 913 ads that spent $100+" is shown beside it. The product tiles, the row panel stat cards, the print intro and the CSV columns `ads_launched`, `ads_under_100_spend`, `ads_100_plus_spend`, `ads_10k_plus_spend`, `hit_rate_10k_of_launched`, `hit_rate_10k_of_tested` (appended after `notes`) all use these counts; "Ads tested" always equals the $100+ count. Excluded: ad families with no launch date and no spend (briefs, ideas), tracker rows deleted from the sheet. Included: renamed re-uploads (each is its own ad family) and relaunch copies, so launched counts run higher than the number of distinct concepts.
* **Last-30-days block.** ROAS, CPA, spend, purchases and ads live are activity inside the 30-day window. The funnel under it is a **launch cohort**, not window activity: ads launched in the last 30 days / 31 to 60 / 61 to 90 days ago (launch date = tracker Launch Date, else first day with spend; snapshot `baselines.<product>.cohorts`), each split by **spend to date**: under $100 / $100+ / $10K+ and the headline "N of M ads hit $10K+". New ads need time to reach $10K, so the older cohorts show what ads that have had time do. Cohort counts include launched ads with $0 spend ("N with spend" shown); the tile's "New ads launched" counts only ads that have spent, so it is smaller. The old window funnel (`funnel_30d`) stays in the snapshot but is no longer shown. CSV appends `ads_launched_last_30d` and `ads_10k_plus_of_launched_last_30d` (per concept) after `roas_14d`.
* **Last 14 days columns** (`Spend · 14d`, `ROAS · 14d`; snapshot fields `spend_14d`, `purchases_14d`, `roas_14d`): per concept, summed from `family_daily` over the 14 days ending at the data-through date, Meta-reported, raw (not shrunk) purchase value / spend. ROAS is blank (a dash) under $100 spend in the window (`MIN_14D_SPEND`); the spend still shows. Manual, proposal, competitor and untested rows show a dash. The ROAS cell is tinted green / red with an arrow when 5% or more above / below the product's last-30-day ROAS. Print strips add `14d: $X at Yx`; the CSV appends `spend_14d`, `roas_14d` at the very end.
* **Scoring is unchanged.** The score's hit-rate component still counts a hit at $1,000 (`HIT_SPEND`) over mature tested ads. Switching it to $10,000 left every status unchanged but moved 14 of 74 scores and the order of 5 rows (hits per line are single digits, so the shrunk rate gets noisy), so display and scoring use separate constants.
* Old snapshots without the funnel / 14-day fields still render (the tile shows the old $1,000 hit rate; no funnel, delta chip or 14-day figures).
* **Product tiles, three blocks** (2026-11-10): ALL TIME, LAST 30 DAYS, LAST 14 DAYS. The 14-day block uses baseline fields `spend_14d`, `roas_14d`, `purchases_14d`, `value_14d`, `cpa_14d`, `live_14d` (ads that spent in the window), `new_ads_14d`, `cohort_14d` (ads launched in the last 14 days split under $100 / $100+ / $10K+ by spend to date) and `spend_14d_no_line` (14-day spend on ads with no line). Each block's delta chips compare with all time.
* **Total row under the table.** Sums `Spend · 14d` of the rows shown (filters, search, selected-only and saved views all change it) and shows ROAS · 14d as total purchase value / total spend (row field `value_14d`), never an average of the cells; a per-product subtotal row (product accent colour) appears when several products are shown. Under it a note per product reconciles with the tile: "shown rows = $X of the product's $Y 14-day spend (Z%)", how much sits on ads with no line, and the rest (lines with no row on this page, i.e. average or too-early lines, or rows hidden by filters). The print copy ends each product section with a total line; the CSV has no total line.
* **Why the table total is not the tile.** On prod (2026-11-09 data) the 74 rows cover about half of each product's 14-day spend; no spend sits on ads with no line, the rest is on average / too-early lines that are not listed.

## Everything else (2026-11-10; now the Hold action, see the redesign table at the top)
* The table lists **every line** now. Rows in an action section (Was working, Iterate, New, Proposed, Competitor, Stop) are unchanged and stay on top; every other line becomes a lightweight row in the last section **Everything else** (neutral gray chip, `section = rest`), sorted by 14-day spend then all-time spend. Panels for these rows are built on first open; no revive play. Older snapshots without `rest` rows render as before.
* **Status labels.** `AVERAGE` lines are labelled **RUNNING AS USUAL**; TOO EARLY, UNTESTED / UNDER-TESTED and NOT WORKING keep their real labels (relabelling them would be false); lines that sit in an action row keep that row's label (FADED / COLLAPSED / STOPPED / WORKING NOW / RISING / NOT WORKING). `Lines by status` counts the underlying status of every line (they add up to the total, 157 on 2026-11-09: Running as usual 37, Too early 37, Untested 51, Not working 15, Working now 11, Rising 3, Fading 3) so a tile can be larger than the number of rows carrying that label (some AVERAGE lines sit in a FADED row).
* **Ads without a line yet** (`line_code = no line`, status NO LINE): one row per product only when some ad family with spend carries no line tag; its panel lists the 15 biggest. On 2026-11-09 data the row does not exist: every ad family with spend is tagged (0% of spend in all three windows) and family-level 14-day spend (the `family_daily` total) equals the three tiles exactly. Ads that have no tracker row at all are in neither the tiles nor the table.
* **Reconciliation.** With no filters, the sum of all rows' `spend`, `spend_30d` and `spend_14d` per product equals the tile (verified on prod: exact to the cent). The totals row and the "shown rows = $X of the product's $Y" note keep working when filters are on.
* **Print** stays the action rows only (selected rows print whatever they are); the **CSV** includes every row (the `section` column distinguishes) with the usual columns.

## Hit-rate strip and chip filters (2026-11-10)
* **Tiles.** Each product tile = ALL TIME stats, LAST 30 DAYS stats, LAST 14 DAYS stats, then one **Hit rate (ads that reached $10K+ spend)** strip with three plain lines: *Lifetime*, *Launched in last 30 days*, *Launched in last 14 days*, each a big % with "N of M launched ads" beneath (ads launched in that period that have spent $10,000+ to date / ads launched in that period). The stacked bars, under-$100 / $100+ funnel text, 31-60 and 61-90 day cohorts and the hits-of-tested wording are gone from the page; they stay in the snapshot (`baselines.<product>.funnel`, `cohorts`, `cohort_14d`, `funnel_30d`) and the CSV columns. The print intro carries the same three rates. Row panels show a plain "Hit rate ($10K+ spend)" card.

Click a chip to show only it; click another to add it (union inside a group); different groups combine with AND; click a selected chip to remove it; removing the last one returns to no filter. "N filters on" counts groups with a selection; Clear filters resets all. Status is multi-select now.

## Production (2026-11-10): giving concepts to vendors
`/priorities` decides what to make; **Production** (`/priorities/production`, linked as **Production** in the header of `/priorities`) tracks who is making it. An **assignment** is one concept given to one vendor to make for one week ("week of" = the Monday that starts the vendor's work week). Table `creative_priorities_assignments` (migration 202) holds it, and `creative_priorities_vendor_links` holds one link token per vendor. A concept stays in the ideation list exactly as it is: assigning never moves, hides or re-labels it (Action and Status do not change). Any row can be assigned: Make more, Revive, Test, Stop, Hold, Add to sheet rows and manual concepts.

**Assigning.** Tick rows on `/priorities`, click **Assign to vendor** in the selection bar, choose the vendor (Madre, Victoria, TrybeDCShop, TrybeOrion, 10xROAS, Internal, PuredMedia, CreateMastery, OpenProgram), the week of (a Monday, this week and the next four, next Monday preselected) and an optional note (500 characters, internal: never shown to the vendor). The dialog then says how many concepts were assigned and lists any that were skipped with the reason (already assigned to that vendor for that week, not in this week's list, no cluster or pain point), with a link to Production. `POST /api/priorities/assignments {keys, snapshot_week, vendor, for_week, note}` takes the **row keys** of the page (`product|action|cluster|icp|pain_point`, or `manual:<id>`; old-section keys still work), not the `ckey`; the server resolves each row from the stored snapshot and stores the concept under `ckey`: `line:<taxonomy line id>`, `manual:<id>`, or `text:<product>|<cluster>|<icp>|<pain point>` for rows with no line (so a draft that later becomes a real line still matches through the stored text key). Assigning the "ads without a line yet" bucket is blocked in the page.

**On `/priorities`.** An **In production** column (not on the public saved-view page `/priorities/v/<token>`, which never loads assignments) shows the latest open assignment of the concept, "Madre, week of Nov 16: Brief sent", plus ", +N earlier" when more are open; open = not launched and not dropped. The row's detail panel ends with **Production history**: every assignment of that concept, closed ones too, with week, vendor, stage, brief and creative links, linked Concept IDs and the result. **Hide concepts already assigned this week** (off by default, counts as a filter) hides concepts that have an open assignment for this week or a later week. The matching is by `ckey` with the stored text key as the fallback. CSV and print output are unchanged.

**Stages** (never stored; derived on every read by `stage_of`, the furthest of the assignment's own facts and its linked Creative Tracker rows): Assigned (nothing yet), Brief sent (brief link added, or tracker status 3 to 5), Creative delivered (creative link added, or tracker status 6), Ready to launch (marked ready, or tracker status 7), Launched (marked launched, or tracker status 8 or 9), Dropped (set aside; restorable). Launched ads are linked by Concept ID (`tracker_concept_ids`, suggested from the tracker when one of its rows carries the assignment's brief or creative link). The result reads "Launched 11/3, $1,240 spent, 1.80 return" from the linked ads' spend and return (Creative Tracker data; nothing is computed from Meta by this feature).

**Production page** (internal, same login as the rest of the app): one plain table of assignments (week of, vendor, product, concept, brief, creative, stage, ads, result) with filters for week and vendor and a switch for launched and dropped ones; briefs and creative links are edited in place; actions are Ready to launch (only with a creative link), Mark launched, Change vendor or week, Drop (confirmed) and Restore; Add Concept ID links the launched ads. Above the table, **Copy link for <vendor>** and **Reset link** (the old link stops working).

**Vendor link pages** (`/priorities/vendor/<token>`, no login, the unguessable link is the access; one link per vendor). A vendor sees only their own assignments (open ones and those launched in the last four weeks), grouped by week: the concept (cluster, ICP, pain point, story), the brief link, stage, linked ads with their spend and return, and the result. They can do exactly three things: add or change the **creative link**, write a **note** to the team, and mark a concept **Ready to launch** (and undo it) once a creative link exists. They never see the internal note, who created the row, suggestions, other vendors' rows, the app's navigation, or links that need a login. Writes are rate limited per IP.

**Nightly tags.** The nightly etl runs `python -m etl.assignment_tags` (non-fatal, recorded in `etl_runs` as `assignment_tags`) right before `etl.auto_tag`: for every open assignment that has a taxonomy line it gives each linked Creative Tracker ad that has no current line tag the assignment's line (`tagger = assignment`, version `assign-YYYY-MM-DD`); it never overwrites or retires an existing tag, and re-running finds nothing new. `--dry-run` prints what it would do.

**What it does not do.** Nothing in Production writes to the Creative Tracker sheet or any other Google Sheet, and nothing talks to Meta: the sheet stays the record of the ad, the app only records who was asked to make which concept and reads the tracker back. The only writes are to the app's own tables (assignments, vendor links) and the nightly line tags above.


## API keys (2026-11-10): read everything, assign on the production board, nothing else
An API key lets a colleague or a script use the app without a login. A key can **read** everything the app serves (every GET under `/api/` and `/media/`, so the numbers, the tags and the production board) and can make exactly **two writes**: assign concepts (`POST /api/priorities/assignments`) and change an assignment (`PATCH /api/priorities/assignments/<id>`: vendor, week, note, brief link, creative link, concept IDs, ready, launched, dropped). Every other write is refused with a 403 and the message "This API key is read only except for assigning items on the production board." That covers saved views, manual concepts, vendor links, vendor link tokens, the ad launch routes, the projection and settings.

What a key can never do: launch ads (launching needs a named login listed in `META_LAUNCH_USERS`, and a key never counts as one), sign in (`/api/login` ignores keys), or read vendor link tokens (`GET /api/priorities/vendor-links` returns the secret links the vendors use, so it is refused for keys). A key is a long random secret (`lvk_` followed by 40 characters). Only its SHA-256 hash is stored, so it cannot be looked up again: if it is lost, make a new one and revoke the old one.

**Make a key** (run against the production database, `DATABASE_URL` set, from the repo):
```
python -m etl.api_keys create --name maria            # prints the key once, to your terminal only
python -m etl.api_keys create --name maria --out ~/maria.key    # writes it to a new file (read and write for you only) and prints nothing secret
python -m etl.api_keys list                           # name, first 8 characters, created, last used, revoked (never the key)
python -m etl.api_keys revoke --name maria            # stops working at once
```
Send the key through a password manager or another private channel, never in a public chat or a committed file. The name shows up in the audit columns: an assignment made with the key above has `created_by` and `updated_by` set to `key:maria`. A key is refused with 401 when it is wrong, revoked or malformed, and 20 wrong keys from one address in 10 minutes lock that address out for the rest of the window (429; `API_KEY_MAX_FAILS_IP` changes the number).

**Read** (put the key in a shell variable first, for example `KEY=$(cat ~/maria.key)`):
```
curl -H "Authorization: Bearer $KEY" https://web-production-358da.up.railway.app/api/priorities/assignments
```

**Assign** a concept to a vendor for a week. `keys` are the row keys of the weekly list, written `product|action|cluster|icp|pain_point` using the `product`, `section`, `cluster`, `icp` and `pain_point` fields of a row from `GET /api/priorities` (a manual concept is `manual:<id>`). `for_week` is any date (it snaps to that week's Monday) and `vendor` is one of Madre, Victoria, TrybeDCShop, TrybeOrion, 10xROAS, Internal, PuredMedia, CreateMastery, OpenProgram. `snapshot_week` and `note` are optional:
```
curl -X POST -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"keys": ["vita-bull|make_more|Energy|Given Up Guy|Low T"], "vendor": "Madre", "for_week": "2026-11-16", "note": "first batch"}' \
  https://web-production-358da.up.railway.app/api/priorities/assignments
```
The answer is `{"created": [...], "skipped": [...]}`; a concept already assigned to that vendor for that week is skipped, not duplicated.

**Update** an assignment (the `id` comes from the answer above or from the read call; send only the fields to change; `ready`, `launched` and `dropped` are true or false):
```
curl -X PATCH -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"brief_url": "https://docs.google.com/document/d/example", "ready": false}' \
  https://web-production-358da.up.railway.app/api/priorities/assignments/12
```
The usual write protections still apply to key requests: JSON bodies only, a request that carries an `Origin` header from another site is refused (scripts that send no `Origin` header are fine), and at most 60 assignment writes a minute per address.
