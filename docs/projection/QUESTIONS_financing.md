# Questions and assumptions (financing)

Each default below is what the module does today; one line changes it.

1. **Levers and series instead of the brief's three tables.** The brief lists `proj_debt_terms`, `proj_debt_payment` and `proj_cash_inputs`. CONTRACT (data conventions) says anything a scenario can change is a lever in `params['financing']` or a series `financing.*`, so scenarios clone and restore with no extra code. Nothing financing-related is scenario-independent, so migration 160 creates no tables: it only seeds `current`.
2. **Grid payload names.** `interfaces.Row.to_dict()` emits `fmt: money|money2|int|pct1` and `kind: line|memo`; `lib/grid.js` expects `usd0|usd|num|pct` and `calc|ratio|input`, and reads `note` and `agg`, which `Row.to_dict()` does not carry. `financing.js` maps the names itself (`toGrid`) and the API adds `note` and `agg` to the rows it returns. Either the core payload or the grid's `normalize` should do this for every module. Mapping is idempotent, so nothing breaks when it moves.
3. **Restore baseline and loader-written cells.** In a scratch database where the drivers seeder wrote its 211 series cells after its first params change, `POST /scenarios/current/restore {version: 1}` removed those cells (the baseline snapshot was taken before they existed). Core's note says loader-written data is restorable; this case is not. Seeders that write series directly should do it before any `scenarios.update`, or the baseline should be captured lazily at the first API write after the data exists. No financing code is involved.
4. **Payback AOV and CAC.** The sheet reads them from `Automated Pacing M6/M7` (month-to-date). Current plan holds the snapshot values (AOV 69.156, CAC 105.492) as typed levers with that source; clearing them (null) falls back to the drivers' last closed month. When the pacing module lands it can pass its own live values to `calc.payback(...)` or write the levers.
5. **Tax.** Tax payments are `rate x net operating income of a period`, paid in a chosen month, never negative. The sheet's first payment multiplies a 4-month total by 4/12 again (details in MODULE_financing.md); the engine taxes the full period. The two later payments tie exactly. Tax base is net operating income as in the sheet (term-loan interest is not deducted; lever `tax.deduct_interest` exists, default off).
6. **Opening cash for Oct-26.** The sheet types 0 (P&L X110), which drops the Sep-26 shortfall of $85,475 from every later month. Seeded as an override cell so the engine ties; clearing it carries the shortfall forward and lowers every later month by that amount. Josh's call which is intended.
7. **Seller note.** Off, as in the sheet. Terms are levers (principal $1.5M, 5%, first installment 2027-09-01, 3 annual installments, interest on the balance each year). The EBITDA floor from the LOI is a flag only (trailing-12-month net operating income vs the floor at each installment); it never gates a payment. The floor amount is not in the sheet; the lever is blank.
