# Questions and assumptions (inventory_supply)

Each line is the default I chose and where to change it. None blocks the module.

1. **Freshness cadence `manual`.** The coordinator asked for `stock_fba` and `stock_intl` to report cadence `manual`. `app/projection/freshness.py` accepts only `daily` and `monthly-upload` and raises for anything else, which would turn all four of this module's feeds into one "freshness hook failed" error. Default: the hook reports `monthly-upload` for the two manual counts (reported, never fatal in `etl.projection_daily`) and adds `input: "manual"`; my own `GET /api/projection/inventory-supply/freshness` and the page keep the word manual. If a `manual` cadence is wanted in the runner, `CADENCES` in `app/projection/freshness.py` is one tuple.
2. **Grid payload `fmt` names.** `interfaces.Table` validates `money / int / num2 / pct1 ...`, but `lib/grid.js` and `format.js` read `usd / usd0 / num / pct / x / text / date` and the kinds `calc / ratio / input` that `Table` rejects. This module builds its payloads by hand with the grid's names (as `MODULE_ui_shell.md` documents) instead of `Table`. A module that uses `Table.add(..., fmt='money')` will not format in the grid; foundation may want to map the names in `Table.to_dict`.
3. **Two Revamp stock feeds.** `inventory_demand`'s refresh also lands Revamp on-hand into its `proj_demand_snapshot`. I read only `proj_stock_snapshot` (editable, append-only, one source of truth) and refresh Revamp into it with `etl.projection_inventory_supply.refresh`. If the demand module's copy should win, change `loaders.load_inputs` to read its latest row per product; the opening rule (Revamp on hand minus allocated) is unchanged.
4. **Reconcile CLI under `strict=True`.** It runs every module, so the database needs every module's migration (all of `migrations/` applied; empty upstream tables are fine). `PROJECTION_TODAY=2026-11-03` pins the reference day; without it the burn starts in the current month and the frozen sheet no longer lines up.
5. **Scenario-aware rows (resolved 2026-11-03, Josh rule).** Stored orders and transfers stay the plan of record (`proj_po`, `proj_fba_transfer`, no `scenario_id`); a scenario copy keeps its own changes in `params.inventory_supply` (`pos`, `transfers`, `vendors`, `prices`, `reorder`, `product_costs` and the scalar variables), so changes are versioned, audited and restorable by the core and never touch the plan of record. Editing the plan of record edits the stored rows. Open: a stored row that the plan of record deletes later leaves a copy's change pointing at nothing; it is skipped and flagged as a data check.
6. **Default vendor facts.** Minimum orders (China 5,000, KeyStone 20,000) and which vendor supplies which location come from the 2026-10-13 rebalance script (`apply_rebalance_2026-10-13.py`), not a sheet tab. They are rows in `proj_vendor_lead`, editable on the page.
7. **Central variables registry.** `app/projection/variables` (VariableSpec) is owned by proj-variables. This module's scalars bind as `binding="param"`, `path=("inventory_supply", <key>)`; the tables are `kind="table"` on page `inventory-supply` and are read with `GET /api/projection/inventory-supply/variables` and written with `PUT .../variables` (item kinds `lever`, `vendor`, `price`, `reorder`, `product_cost`, `po`, `transfer`). No `specs_inventory_supply.py` was written here (not an owned path).
